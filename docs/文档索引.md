## 一、权威顺序（冲突时听谁的）

不同类型的问题，真源不同 —— **不要用一句话概括「谁最大」**：

| 问题类型 | 真源 | 说明 |
|---|---|---|
| 版本号、行号、数据结构、函数行为、接口清单 | **代码** | 本文档集只是地图；代码变了地图要跟着改 |
| UI 样式 / 组件类 / 文案句式 / 版本号规则 | **`UI规范.md`** | 代码与规范不一致 → 视为**代码偏差**，应改代码或修规范，二者必须收敛 |
| 操作流程（怎么跑、怎么验、怎么发） | **`docs/项目运行与开发上手说明.md`** | 与代码冲突时以代码为准并回改文档 |
| 仓库身份、与上游的关系 | **`docs/本仓库身份与FoodIn的关系.md`** | 历史事实，不做技术判断 |
| 历史决策与踩坑过程 | **`docs/开发经验总览.md`** | 经验类，允许滞后；与代码冲突时以代码为准 |

**通用兜底**：`docs/archive/` 下的一切**不作为开发依据**，只作追溯。

## 四、文档维护规则

1. **改代码导致事实变化 → 同一次提交里改文档**（版本号、行号、接口清单、数据结构）。
2. **文档失效时的处理是「归档」而不是「原地加批注」**：移到 `docs/archive/` 并加横幅，避免两份说法并存。
3. **规则类事实只在一处定义**：例如「版本号怎么 bump」只在 `UI规范.md` §八 定义，其他文档只引用不复述。
   （版本号对照表属于速查，可在多处出现，但**以 `docs/CHANGELOG.md` 顶部为准**。）
4. **禁止在文档里写「大概 / 可能 / 建议确认」这类模糊结论** —— 要么给出可验证的判定方法，要么标为「待决」。
5. 行号引用必须带函数名或锚点文本（`saveData`(6204)），便于行号漂移后重新定位。
